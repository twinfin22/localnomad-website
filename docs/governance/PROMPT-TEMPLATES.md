# Prompt Template Library (프롬프트 템플릿 라이브러리)

> **목적**: Claude Code에 넘기는 실행 프롬프트의 품질을 표준화.
> Gen님도 직접 프롬프트를 작성할 수 있도록 검증된 구조를 템플릿화.
> Day 1-7 프롬프트 중 잘 작동한 구조를 기반으로 작성.

---

## 프롬프트 작성 원칙

1. **Gen님이 뼈대를 잡고, Claude가 살을 붙인다**
2. **성공 기준(Success Criteria)을 먼저 정의**
3. **수정할 파일 목록을 명시** — "알아서 찾아서 고쳐"는 금지
4. **검증 단계를 포함** — 빌드 + Gen 직접 확인
5. **금지 사항을 명시** — suppressHydrationWarning, eslint-disable 등

---

## Template A: 버그 수정 프롬프트

```markdown
# [버그명] 수정 프롬프트

## 목적
[한 문장으로 무엇을 수정하는지]

## 배경
[왜 이 버그가 발생하는지, 근본 원인]

## 수정 대상 파일
| 파일 | 변경 내용 |
|------|----------|
| `경로/파일.tsx` | [구체적으로 뭘 바꾸는지] |

## 수정 방법
[Gen님이 선택한 접근 방식]
[구체적인 코드 변경 사항 — before/after]

## 금지 사항
- suppressHydrationWarning 사용 금지
- eslint-disable 사용 금지
- @ts-ignore 사용 금지
- 명시되지 않은 파일 수정 금지

## 검증
1. `npm run build && npm run lint` 성공 확인
2. Gen님이 직접 확인할 항목:
   - [ ] [구체적인 확인 사항 1]
   - [ ] [구체적인 확인 사항 2]

## 롤백 기준
[어떤 상황이면 전체 되돌리는지]
```

## Template B: 기능 추가 프롬프트

```markdown
# [기능명] 추가 프롬프트

## 목적
[한 문장으로 무엇을 만드는지]

## 성공 기준 (Gen님이 정의)
- [ ] [기능이 정상 작동하는 조건 1]
- [ ] [기능이 정상 작동하는 조건 2]

## 실행 흐름 (5단계 이내)
1. 서버에서: [뭘 하는지]
2. 브라우저에서: [뭘 보여주는지]
3. 사용자가: [뭘 할 수 있는지]

## 수정/추가 파일
| 파일 | 작업 | 내용 |
|------|------|------|
| `경로/파일.tsx` | 수정 | [뭘 바꾸는지] |
| `경로/새파일.tsx` | 추가 | [뭘 만드는지] |

## 데이터 구조 (있는 경우)
[JSON 스키마, 타입 정의 등]

## 법률 확인 (해당 시)
- [ ] CLAUDE.md Legal Bright Lines 준수 확인
- [ ] "you qualify", 점수, 퍼센티지 등 금지 표현 없음

## 금지 사항
- components/ui/ 수정 금지
- 명시되지 않은 패키지 설치 금지
- suppressHydrationWarning 사용 금지

## 검증
1. `npm run build && npm run lint`
2. Gen님 직접 확인:
   - [ ] [확인 사항]

## 롤백 기준
[조건]

## 문서 업데이트
- [ ] TECH-DEBT.md (새 부채 있으면)
- [ ] DECISION-LOG.md (의사결정 있으면)
- [ ] ARCHITECTURE-MAP.md (구조 변경 있으면)
```

## Template C: 감사/분석 프롬프트

```markdown
# [감사 대상] 감사 프롬프트

## 목적
[무엇을 점검하는지]

## 점검 기준
[어떤 기준으로 위반/문제를 판단하는지]
- 기준 1: [예: CLAUDE.md Legal Bright Lines]
- 기준 2: [예: 대만 이민법 §56]

## 점검 범위
- 파일: [어떤 폴더/파일을 검사하는지]
- 패턴: [grep으로 찾을 키워드]

## 출력 형식
| # | 심각도 | 파일 | 라인 | 문제 | 수정 방안 |
|---|--------|------|------|------|----------|

## 결과 저장
`docs/reports/[감사명]-report.md`
```

```markdown
## 목적
[어떤 데이터를 어떻게 바꾸는지]

## 변경 대상
| 파일 | 필드 | 변경 전 | 변경 후 |
|------|------|--------|--------|

## 영향 범위
[이 데이터를 사용하는 페이지/컴포넌트]

## 검증
1. `npm run build`
2. 해당 페이지에서 변경 내용 확인
```

## 검증된 프롬프트 사례 (잘 작동한 것)

| 프롬프트 | 파일 | 결과 | 잘된 이유 |
|---------|------|------|----------|
| LEGAL-FIX-PROMPT.md | 8개 Task | ✅ 6/6 위반 수정 | 파일별 구체적 변경 사항, before/after 코드 명시 |
| SPRINT-0-PROMPT.md | 5개 Task | ✅ 빌드 성공 | Prerequisites(사전 조건)가 명확 |
| FLICKER-FIX-PROMPT.md | 6개 Task | (실행 전) | 각 Task별 선택지를 Gen이 결정 후 작성 |

## 실패한 프롬프트에서 배운 것

| 문제 | 원인 | 교훈 |
|------|------|------|
| Hydration 수정 후 flickering 지속 | 레이아웃만 고치고 컴포넌트는 안 건드림 | **수정 대상 파일을 정확히 명시**해야 함 |
| Puppeteer 검증 오판 | 테스트 범위가 너무 좁음 | **검증 범위를 Gen이 정의**해야 함 |
| suppressHydrationWarning 남용 | 금지 사항 미명시 | **금지 사항 섹션 필수** |
